## 1. 对账是怎么做的（方法学）

同一份 **JSON 夹具** `src-tauri/crates/rules/tests/data/m3-parity.json` 被两侧读**同一份字节**：

> 夹具目录叫 `tests/data/` 而不是 `tests/fixtures/`：本仓 `.gitignore:6` 有一条 `fixtures/`，
> 放那儿会让夹具**被静默忽略**（提交里没有它，测试在别的机器上找不到 —— 而"没跑"与"通过"长得一样）。

- TS 侧：`scripts/parity-rules.mjs` —— 现跑 `core/rules`（行为基准），吐原始报告 JSON；
- Rust 侧：`tests/parity_with_ts.rs` —— 现起 `esbuild` + `node` 跑上面那个脚本，再把两份报告
  投影成同一个形状逐字段比。

三条纪律（都对应本项目记过账的坑）：

1. **两侧看同一棵树**。若各扫各的树，M1/M2 的口径差会被误判成引擎差 —— 而这一层要判的
   恰恰是"引擎对同一输入的结论是否相同"。
2. **归一化只在一处发生，且两侧共用同一个投影函数**。两侧各自归一化到"看起来一致"，
   会把真差异抹平（那正是"互相印证的数共享同一个盲区"）。
3. **缺工具（node/esbuild）时大声失败，不静默跳过**。静默跳过的验收等于没有验收。

夹具 4 个 case 各自要打的一类事：

| case | 打什么 |
| --- | --- |
| `builtin` | 15 条内置规则 + 一棵贴近真机形状的树（Temp / Chrome 多 Profile 通配 / 回收站 / `System32` / 带 SYSTEM 的文件 / 没扫到的地盘 / 缺变量的路径） |
| `gates` | 评估层判据：`olderThanDays`、`recursive=false`、`filePatterns`、探测器判未装、变量缺、没扫到、递归深树 |
| `blocked` | fail-safe：`%WINDIR%` 缺失 ⇒ 禁止根解析不出来 ⇒ **一份结论都不许给** |
| `static` | 声明层判据：裸容器 / 通配收尾 / 非 🔴 认领回收站 / 套住禁止根 / 相对路径 / 规则间祖先 |

**零容差的一致性结果**：

```
builtin | findings=15 | exclusions=12 | rejected=[]                     | reclaimable=1640 | blocked=false
gates   | findings=6  | exclusions=4  | rejected=[]                     | reclaimable=1585 | blocked=false
blocked | findings=0  | exclusions=5  | rejected=["t","n"]              | reclaimable=0    | blocked=true
static  | findings=2  | exclusions=6  | rejected=[六条]                  | reclaimable=600  | blocked=false
```

`builtin` 的逐条字节（两侧逐字相同）：`windows-temp:300 browser-cache:180 thumbnail-cache:40
shader-cache:0 error-reporting:25 recycle-bin:500 npm-cache:800 pip-cache:25 gradle-cache:0
vscode-cache:185 maven-repository:0 pnpm-store:30 yarn-cache:35 huggingface-cache:0 android-sdk-temp:20`。

## 2. 抓到的 4 个真缺陷

对账第一次跑就是**红的**（4 个 case 全红）。逐个归因如下；每个都先看到红、再修、再绿。

### 2.1 `ScanFile` 不带文件属性 ⇒ §28 原则二的判据在 Rust 侧永不触发（方向：多删）

- **症状**：夹具里 `attrs=4`（SYSTEM）的 `sys.tmp`，TS 排除、Rust 认领。
- **根因**：`ScanFile` 结构里根本没有 `attrs`；枚举层其实**已经拿到了**这一位
  （`FileIdBothDirectoryInfo.FileAttributes`），只是没往下传。
- **为什么危险**：方向是"Rust 认领一个 TS 会保护的文件" —— 执行器吃的是这份清单。
- **修法**：`ScanFile.attrs` 从枚举一路带到评估层；同时修掉 `to_view()` 里对文件硬写的 `Some(0)`
  （那是一句谎，§28 原则二的判据读的正是它）。
- **证据**：`tests/engine_real.rs::a_real_system_attributed_file_is_excluded_on_a_real_tree`
  —— 真给文件打 `SetFileAttributesW(FILE_ATTRIBUTE_SYSTEM|FILE_ATTRIBUTE_ARCHIVE)`，
  断言"认领合计 = 整层合计 − 该文件字节"。
  **变异证明**：把适配器的 `attrs: Some(f.attrs)` 改回 `None`，该用例与内置表用例双双打红。

### 2.2 探测器判「工具没装」的规则仍然产出一条 0 字节 finding

- **症状**：`gates` case 的 `findings` 条数 Rust=7 / TS=6。
- **根因**：`evaluate_rule()` 在"没装"分支里 `return finding(...)` —— 与它自己的注释
  （"一条 finding 都不出"）矛盾；TS 那边是 `continue`，压根不 push。
- **修法**：抽出 `exclude_rule_as_not_installed()`，真的不 push finding。

### 2.3 声明层缺两条判据，其中一条被"逐条调用"结构性关掉（方向：多删）

- **症状**：`static` case 里 `%LOCALAPPDATA%`（裸容器）与"套住别家叶子"的规则
  TS 拒、Rust 放行；放行的那条还先认领了文件，把本该属于别条规则的字节吃掉了。
- **根因有两个**：
  1. `CONTAINER_VARS` 只有 6 条（TS 10 条），且**没有** `BROAD_LEAF_NAMES` 这张表；
  2. `evaluate_rules` 里是 `validate_rule_set(&[rule])` —— **逐条**调用。
     "本规则的地盘是不是别条规则的严格前缀"这条判据只有看到全表才判得出来，
     逐条调用等于把它**静默关掉**。`engine.rs` 里还留着一条指向
     `ShapeProblem::BroadContainer` 的注释，而那个变体当时并不存在。
- **修法**：`validate_rule_set` 收**整表**，判据顺序与名单逐条对齐 TS `validateRuleSet`；
  `CONTAINER_VARS` 补齐 10 条、新增 `BROAD_LEAF_NAMES`。

### 2.4 `safetyBlocked` 只置位，却照旧把 findings 算完

- **症状**：`blocked` case 里 TS `findings=[]`、Rust 有 findings。
- **为什么危险**：保护失效时报告里仍躺着一份"可清理清单"，消费方一旦漏检这个标志就会拿它去执行。
- **修法**：fail-safe 时**早退** —— `findings` 空、`reclaimable_bytes` 0、
  全部规则记进 `rejected_rules`，并为每个解析不出来的模板点一条
  `forbidden-root-unresolved` 排除（新增该 `ExclusionReason` 成员）。

### 2.5 交接叙述里那条"顺序无关"的对账（不是上面 4 个之一，但同批修掉）

`builtin.rs` 的 15 条规则**顺序与 `registry.ts` 不同**（Rust 把 §21 批次排在 §26 批次之前），
而它自己的顺序测试把这个错序固化了、注释还写着"与 registry.ts 逐字相同"。
`claimed` 表是先声明者计账 ⇒ 顺序不同就是两套事实源。已按 TS 顺序改正。

## 3. 有意保留的差异 / 已知缺口（诚实清单）

对账把下面这些**显式记录**下来，而不是让它们藏在"归一化"里：

| 项 | 状态 | 说明 |
| --- | --- | --- |
| 规则表**重号** | **共同缺口**（两侧都不拦） | Rust 原有的 `DuplicateId` 判据被**移除**以与 TS 对齐（TS 的 `validateRuleSet` 没有这条）。留一条只有一侧有的闸，下一个人很快会遇到"Rust 拒了 TS 没拒"而无法判断该信谁。要补就两边一起补。 |
| `rule-rejected` 排除项**不带出问题的路径** | Rust 侧缺口 | TS 那条排除点名到出问题的 `path`，Rust 目前只写 `""`（原因在 `detail` 里）。对账时**显式忽略**这一格而不是假装一致。 |
| `RuleFinding` 缺 `category` / `cleanStrategy` | **已闭合（2026-10-11，M3-B Task 1）** | 原先 Rust 的 finding 不带这两个字段。M3-B 的预览要用（`cleanStrategy` 决定执行口径），已补齐并**纳入零容差对账**（`parity_with_ts.rs` 的投影现在逐字段比 findings 的 `category` / `cleanStrategy` / `recoverable`）。 |
| `open_dir` 查不到目录时**不记 `not-scanned`** | **实测不可达，不修** | TS 的 `openDir` 会记一条；Rust 不记。但 `open_dir` 只被 `expand_step` / `collect_territory` 调用，而入参目录在这之前都已由 `dir_id_by_path` 证明存在 ⇒ 该分支两侧都到不了。**不改**（加一条结构性不可达的分支只会让人以为它测到了什么）。 |
| `--test` 对账**需要 node + node_modules** | 构建前提 | `tests/parity_with_ts.rs` 现起 `node` + `esbuild`。缺了会 panic 并提示 `npm i`，**不静默跳过**。 |
| 文件 `attrs` 进了 M2 的线格式 | **有意副作用** | `TreeIndex::to_view()` 对文件的 `attrs` 从硬写的 `Some(0)` 改成真值（对应 TS `tree-store.ts:125` 的 `attrs: f.attrs`）。方向是"界面终于读得到真属性位"，M2 的几何/容量判据不受影响。 |

## 4. 真盘判据（`tests/engine_real.rs`）

自建临时夹具（跑完自删；**不用** `D:\deepclean-fixture\` —— 那台机器上才有的路径会让判据
在别的机器上静默不跑，而"没跑"与"通过"长得一样）：

- `a_real_system_attributed_file_is_excluded_on_a_real_tree` —— 见 2.1；
- `the_named_all_paths_agree_with_the_count_and_the_total` —— `all_paths` 与
  `file_count` / `total_bytes` 同口径，且合计不超过地盘子树的合计；
- `a_territory_that_was_not_scanned_is_named` —— 没扫到的地盘点 `not-scanned`，不安静算 0；
- `the_builtin_table_evaluates_cleanly_on_a_real_tree` —— 15 条在真树上跑通、账目自洽。

一条**口径提醒**（写在这里免得下一个人当成缺陷）：真盘上 `counted` 是**分配口径**，
MFT 常驻文件的 `AllocationSize` 按 8 字节对齐（100 字节 → 104）。所以真盘判据写的是
**关系式**而不是写死的字节数。
