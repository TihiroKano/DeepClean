## C-1：授权闸与 TS 的零容差对账

**状态：已完成**

### 结论

- Rust `deepclean-cleaner::gate` 与 TS `core/clean/executor.ts` 的授权闸在**同一份夹具**上逐字段相等。
- 对账覆盖：
  - 全部 12 个 `CleanBlockerReason`（`guard_authorized_root` ↔ `guardAuthorizedRoot`）。

### 「回收站计数 +1」这条为什么必须有（变异证明）

把 `fFlags` 里的 `FOF_ALLOWUNDO` 拿掉（= 永久删除）后重跑：

| 判据 | 变异后 |
| --- | --- |
| `real_recycle_under_authorized_target_only`（读 `task.deleted[].ok`） | **仍然绿** |
| `executor_uses_recycle_bin_with_allowundo`（grep 源码里的字面量） | **仍然绿** |
| `recycle_actually_lands_in_the_recycle_bin_not_just_in_the_task_report` | **红** —— 计数停在 14，文件已离开原路径 |

也就是说：**任务回执与静态 grep 闸都看不见「永久删除」这个缺陷**。回执说 `ok = true` 只证明 `SHFileOperationW` 返回 0，不证明东西进了回收站；`use` 语句里那个字面量在 `fFlags` 不引用它时依然在。唯一量到它的是 Shell 自己的回收站计数。
（这与本项目「两侧同口径的对账相等不是验证」「读源码的 grep 闸弱于行为断言」是同一族。）

### 一条 refusal 在公开入口上不可达（如实记，不拿假夹具凑）

`forbidden-root` 的**第二遍**（授权根**之内**命中禁止路径）走不到：Windows 路径的祖先是全序的，一条路径既在授权根内又落在禁止根内 ⇒ 授权根与禁止根必有一个套住另一个 ⇒ 分别被 `root-forbidden` / `root-ancestor-of-forbidden` 在守卫处拒掉。
TS 执行器同一处（`executor.ts:380`）是同样的死分支，**没有替它改行为**。
判据 `a_forbidden_path_inside_the_authorized_root_cannot_be_built_past_the_guard` 钉的是「不可达」这件事本身：守卫一旦被改弱到能构造出这种批次，它会红。
`forbidden-root` 这个 reason 的覆盖由「授权根**外**命中禁止根」那条提供，13 条覆盖不减。

### 两条真 FS e2e 必须串行

它们共用同一个靶场目录与**同一台机器的回收站计数**。并行实测互相污染读数：一条把另一条的探针文件算进 `files_before`（差值 2 而非 1），另一条把回收站计数抬了 2 而非 1。回收站是机器级状态，crate 内隔离不了，故用 `REAL_FS_LOCK` 串起来。

### 顺带修掉一个零报错漏算

`RemoveOutcome::Vanished` 的**两个消费臂一直都在，生产者从来没有过** —— 于是「lstat 之后、recycle 之前目标被别的程序删掉」会被记成删除失败，而 TS `executor.ts:497` 明令「记『跳过』，不冒充删除失败」。
说话的唯一信号是 `dead_code` 警告（`variant Vanished is never constructed`），而没人看警告。
判据：`a_target_that_vanished_mid_batch_is_skipped_not_failed`。
**这条也说明上面那条「静态闸弱于行为闸」的教训在本轮又兑现了一次**：`grep` 型判据看不见缺生产者，编译器看得见。

### 「改措辞不换口径」为什么换成行为判据

第一版是 grep：在 `build_journal` 函数体里搜 `detail.as_str()` 之类。它当场咬到自己 ——
`plain(Some(r.detail.as_str()))` 是**照抄进 `error` 那一格**，那是这一列的本职，不是判定。
grep 分不清「照抄」与「据此判定」，所以换成行为版：
`prose_wording_never_moves_the_journal_caliber` 拿两条只差 `detail` 句子的任务，断言 `status` / `size_bytes` / `risk` / `rule_id` 逐字相同、只有 `error` 变。
（grep 版保留，但 needle 收窄到 `detail.contains` / `starts_with("命中` 这一类真判定形状。）

### 执行链的形状（安全边界落在哪）

`dc_execute(confirmationDigest)` 是**唯一**会动文件系统的入口，且：

- 只认指纹。清单是 `confirm=true` 那一刻由主进程从**报告的认领表**里另取的
  （`executable_paths`：整项勾选的 `preview.items[].paths` 是空的，必须回到 `finding.all_paths`）——
  渲染端报上来的路径清单一律不作数。
- 授权根 = 会话扫描根。扫的是 `C:\` ⇒ 守卫回 `root-is-drive-root` ⇒ **整批拒绝、零删除**。
  这是刻意的（§28 原则四），不是缺陷。
- 取消把手在开跑**之前**注册。执行器每条都查它，所以 `dc_cancel_cleanup` 中途有效。

### 2026-10-11 补：为补这张截图试过的三条路，以及为什么都停手

**待隔离的疑点**，不写成缺陷。要证实只需一步：起一次极小目录的 `DC_AUTOSCAN`，再调一次
`dc_snapshot` —— 后端早已 `completed` 而前端仍是空，即成立。

下的真缓存，或者依赖"守卫在 `C:\` 上一定拦得住"这个假设。前者越出授权范围，后者是拿系统盘赌一张截图。

#### 顺带结掉两个记录在案的疑点

- **`DC_AUTOSCAN` 那条「待隔离疑点」不成立了**：真机复现出来的症状（扫描结束而界面不动）
  根因是我脚本的等待条件写错 —— 扫完 App 会**自动跳进空间地图**，首页随之卸载，
  「查看扫描结果」那个按钮根本没机会出现。换成等地图工具栏就正常。
  订阅竞态本身**仍未被证明存在**，也没有反证；本节把它从"疑点"降级为"未观察到的假设"，
  不再当作已知风险记账。
- **PowerShell UIA 的一个静默陷阱**（值得单独留一句）：`PropertyCondition` 的三参
  （`MatchSubstring`）构造在 PowerShell 里取不到重载，直接抛
  `Cannot find an overload for "new" and the argument count: "3"`。
  我把它包在 `try { … } catch { return $null }` 里，于是**每一次元素查找都静默失败**，
  表现成"页面没渲染"，而真相是查询条件构造不出来 —— 三次失败运行都白跑了十几分钟。
  判据：自动化脚本里"找不到元素"的分支不许吞异常返回空，至少要把异常原话打出来。
  现改成 `FindAll(TrueCondition)` + PowerShell 侧 `-like` 过滤。
- 另一条同类：`-like '*我了解*'` 命中的是复选框旁边的 **Text 标签**，而 Text 不吃
  `InvokePattern` ⇒ 抛 `Unsupported Pattern`、勾选没打上、「开始清理」一直禁用。
  复选框要按 `ControlType.CheckBox` 取 + `TogglePattern.Toggle()`。
