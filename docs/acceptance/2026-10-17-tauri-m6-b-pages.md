## 二、Task 5：那条真判据第一次量出数 —— 八页里六页只剩骨架那一块玻璃

判据（`glass-inventory.mjs` 文件头立的）：一页"有玻璃" = DOM 里存在至少一个
`getComputedStyle(el).backdropFilter !== 'none'` **且面积 ≥ 视口 5%** 的元素。
静态侧写量不到这一格（没有布局引擎 ⇒ 既没 computed style 也没面积），所以必须在真机量。

端口不是产品开的：`WEBVIEW2_ADDITIONAL_BROWSER_ARGUMENTS=--remote-debugging-port=9223`
由**启动环境**注入，WebView2 运行时自己认它，shipped 二进制里没有为验收留的任何后门
（与 `DC_ENV_ROOT` 同一纪律）。

**扫过 `f100k` 之后量的**（不扫就量，带卡片的那几页会停在空态，量到的不是产品的样子）：

| 页 | 有 backdrop-filter 的元素数 | ≥5% 的**内容**面（扣掉骨架 `dc-side`） |
| --- | --- | --- |
| 首页 | 5 | `dc-panel-main` 27.8%、`dc-home-cards` 22.3%、`dc-panel-side` 15.3% |
| 空间地图 | 4 | `dc-side-panel` 24.0%、`dc-bar` 5.2% |
| 大文件 | 8 | **无** |
| 垃圾清理 | 8 | **无** |
| 重复文件 | 1 | **无** |
| 开发环境 | 1 | **无** |
| 清理记录 | 2 | **无** |
| 设置 | 1 | **无** |

原始数据入库在 `assets/m6b-glass-scanned.json`。

两点要连着读，否则会读反：

1. **`大文件`/`垃圾清理` 各有 8 个元素带 blur，但没有一块 ≥5%** —— 玻璃落在小件上
   （chip、按钮、行内块），主内容面板是平的。所以"这页有没有玻璃"取决于判据挑哪一维：
   按"有没有 blur 元素"算，八页全有（那等于没判据）；按"内容面上有没有一块够大的"算，六页没有。
2. 静态侧写（`glass-inventory.mjs`）说 `cleanup` 有 4 个可达玻璃类，真机说它 0 块够大的面 ——
   **两边不矛盾**，是两条轴：源码可达 ≠ 画面上占地方。这正是当初不把页面级 grep 当判据的理由。

另外记一条量具自身的坑：这份汇总第一版把 `dc-side-panel`（24% 的内容面板）当成骨架剔掉了，
因为过滤器写的是 `startsWith('dc-side')`。形状就是本仓那条老教训 —— **同名不同义**：
`dc-side`（左侧导航栏，骨架）与 `dc-side-panel`（地图页右侧详情面板，内容）是前缀碰撞。
改成按 class **token 逐字相等**匹配之后才是上面这张表。

## 三、Task 4：八页 × 三档宽度的溢出矩阵（同一台机器，150% 缩放）

载体 `scripts/m6b-scale-e2e.ps1` + `scripts/scale-probe.mjs`（还是那条 CDP 通道，端口由启动环境注入）。
窗口用 `MoveWindow` 改宽，**先 `SetProcessDPIAware()`** —— 不声明的话给的宽度会被系统按 1.5 倍虚拟化，
那三档就白跑。物理宽与 CSS 视口宽两件事分开报（1440/880/760 物理 ⇒ 960/572/492 CSS，`dpr=1.5`）。

判据有**两条轴**，第一条是我第一版只写了的那条，第二条是量具升级后补的：

| 轴 | 判据 | 结果 |
| --- | --- | --- |
| ① 撑出横向滚动 | `document.scrollWidth > innerWidth` | **24 格全 0**（无一格） |
| ② 越过右缘且**滚不到** | 有元素 `right > innerWidth`，且它的祖先链里**没有**任何 `overflow-x: auto/scroll` 且真可滚的容器 | **1 格** |

②这一格就是缺陷：**760 物理 / 492 CSS 下的空间地图页，`aside.dc-side-panel` 宽 320，
越过视口右缘 28 px，而它没有任何可滚的祖先 ⇒ 那 28 px 用户无论怎么滚都看不到。**
同一档下 `垃圾清理` 的 `table.dc-clean-table` 越缘 88.9 px，但它的祖先 `div.dc-table-wrap`
是可滚容器 —— **那不是缺陷，是要滚一下才看到**，两种形状必须分开，否则要么误报要么漏报。

**为什么这条值得单独加一轴**：`①` 单独用的时候这一格是**绿的**。根不产生横向滚动条，
是因为多出来的那一截被 `overflow: hidden` 吃掉了 —— "没有横向滚动条"在这里不是排版没问题，
是内容没了。"开窄窗拍几张看看"同样看不见：截图右边那 28 px 就是没了，画面看着完整。

矩阵原始数据 `assets/m6b-scale.json`（24 格，每格带 `innerW / scrollW / overflowPx / worst{tag,cls,overPx,reachable,via}`），
三档各一张表格页截图 `m6bscale-{1440,880,760}w-largefiles.png`。

顺带把两处旧说法钉掉：
- `m5m-narrow-window-e2e.ps1` 文件头那句「CSS 里 `@media (max-width: 900px)` 那一段是真的存在」是**假的**：
  `global.css` 与 `glass/tokens.css` 里 `@media` 计数都是 **0**，整个渲染端**没有任何断点**，
  窄窗行为全由 flex 与 `table-layout` 撑着。这条本身要登记的缺口，本轮没动（补断点是设计取向）。
- 那一棒绑 `DC_ENV_ROOT` ⇒ 在 release 上跑不了。这一棒**不认领任何规则领地**，只量排版，
  所以它能落在 shipped 二进制上 —— 这也是为什么是新脚本而不是改 `m5m`。

**这一格按裁定未修**：改 `dc-side-panel` 的宽度策略要动 `global.css`，动完要重打包 + 复跑
Task 6 那条测量链（含两次 UAC）。按 Task 3 Step 4 的规矩"发现的不一致当场登记，别顺手改"，
留作用户点头后单独一批。脚本本身**现在会红**（`②=1 格` 就 throw），修好之前它不该被改成绿。

### 5.1 上面那一格修完是**假绿**，被第三条轴抓回来

按上表那样改完，矩阵两条轴当场全绿（24 格：撑出滚动 0、越缘滚不到 0）。
但我去量了一下面板实际占多少 —— **760 物理 / 492 CSS 下画布宽 = 0**：
可用宽只有 292（492 扣掉 200 导航栏），首栏 `minmax(0,1fr)` 的下限是 0，
于是面板把 292 全吃了，**这一页存在的理由（那张地图）整个没了**。
"没有溢出"从"排版没问题"变成了"主内容被挤没了"，而两条轴都看不见这件事。

于是补第三条轴，并把首栏下限从 `0` 改成 **`180px`**（CSS 与判据用同一个数，两处必须一起改）：

| 窗口物理宽 | CSS 视口 | 画布宽（改前 → 改后） |
| --- | --- | --- |
| 1440 | 946 | 426 → 426 |
| 880 | 572 | **0** → 180（面板退到 192） |
| 760 | 492 | **0** → 180（面板退到 112） |

三条轴现在一起绿：`MATRIX cells=24 撑出横向滚动=0 越过右缘且滚不到=0 画布被挤没=0`。
**这条轴是定点判据，不推广**：它只认地图页那块 `.dc-map-canvas`，因为只有它有"整页就是为这块画而存在"的属性。
写成"任意页最宽元素 ≥ 视口 X%"会绿得毫无意义 —— 窄窗下最宽的永远是那根撑满的容器。

## 六、全站隐藏滚动条（2026-10-17 追加要求）—— 规则加了，但**本机量不出它生效**

改动：`global.css` 顶部 `*` 那一条加 `scrollbar-width: none` / `-ms-overflow-style: none`，
外加 `::-webkit-scrollbar` 一族 `display:none; width:0; height:0`。
这份主题此前从没给滚动条上过任何样式（本文件 `scrollbar` 出现 0 次），所以露出来的是内核默认条。

### 6.1 我原本给它加了一条"证明条被藏住"的判据，然后发现那条判据是瞎的

矩阵第四轴最初写成：对每个"真能滚"的元素量 `offsetWidth - clientWidth`，>1 就算"条还在"。
跑出来 13 个可滚元素全部 0 —— 看着像"藏住了"。做了三步反证之后，这个 0 **不能证明那件事**：

1. 造一个 220×150、内容 900×900、`overflow: scroll` 的盒子（一定该出条），量得 `takenY = 0`；
2. 在页面里**删掉我们那条隐藏规则**（`sheet.deleteRule` 实删 1 条），再量 —— 还是 0；
3. 用真滚轮事件（`Input.dispatchMouseEvent` 的 mouseWheel，`scrollTop` 确实走到 360）在滚动瞬间
   用 CDP 截同一块区域，**加规则与删规则两张图逐字节相同**。

对照实验证明截图通道不是瞎的：把那个盒子背景从红改绿，同一 clip 的两张图 sha 就变了。
⇒ 结论是这台机器的 WebView2（Edg/155.0.4283.60）用**覆盖式滚动条**：它既不占布局，
在这次能构造出的所有情形下也没被画出来。所以第四轴现在的措辞只声明它量得到的事：
**布局没被条吃掉 + 程序化滚动仍然有效**（13 个可滚元素全滚得动），不含"看不见条"。

### 6.2 那这条规则留不留？留，但按它真实的身份留

它是**跨内核的保险**：目标机若开着"始终显示滚动条"、或 Windows 版本/内核用的是经典条，
`::-webkit-scrollbar { display:none }` 是唯一能让它不出现又不占地方的写法。
它在本机不是"已验证生效的修复"，也不能被写成那样。
**确定的代价**：长列表与窄表少了一个"这里还能滚"的视觉提示 —— 这条代价在覆盖式滚动条上其实已经存在
（本来就没有常驻条），在经典条的内核上才会真的显形。
