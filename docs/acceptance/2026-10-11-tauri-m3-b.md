## 1. 对账怎么做的

同一份 JSON 夹具 `crates/cleaner/tests/data/preview-parity.json` 被两侧读**同一份字节**：

- TS 侧 `scripts/parity-preview.mjs`：现跑 `evaluateRules` → `buildPreviewModel`，吐原始模型；
- Rust 侧 `tests/preview_parity.rs`：现起 `esbuild` + `node` 跑上面那个脚本，
  再用**自己的引擎**从同一棵树算出报告、喂给 `build_preview_model`，两边投影后逐字段比。

**归一化只有一处**：摘掉每个 `detail` 键（措辞不是契约）。其余逐字节比，含 `digest`。
`diff_report` 不做白名单点名 —— 只比几个键会让新增字段的差异打印成一段**空报告**。

6 个 case 各打一类事：`mixed`（🟢/🟡/🟠/🔴 同屏 + 不可再生提示）、`paths`（逐路径定价 + 两条保护闸
+ 未枚举 + 重复路径）、`truncated`（采样截断 + `allPaths` 全量定价）、`malformed`（`items` 非数组）、
`bads`（缺 ruleId / 未知 id / paths 非数组 / 非字符串元素 / 声明白名单外的规则 / 重复整项）、
`blocked`（fail-safe：禁止根解析不出来）。

## 2. 判据会红吗（变异证明）

| 变异 | 预期 | 实测 |
| --- | --- | --- |
| `digest.rs` 的路径排序从 UTF-16 码元序改成 UTF-8 字节序 | 对账红，且**只红在 emoji 那个 case 的 `digest`** | ✅ 红；`paths` 的 digest `5035fcfe…` vs TS `e3dbc61e…`，其余字段全等 |
| 适配器不再传文件 `attrs`（M3-A 的证明，此处沿用） | 真盘判据红 | ✅ 见 M3-A 验收 |

**为什么必须有这条**：TS 的 `charCodeAt` 走 UTF-16 码元，Rust 若用 `chars()` 或字节，
只在**补充平面**（emoji / U+E000 以上）上分叉 —— 那是"测不到就不报"的一类错。
夹具里放的是 `x-😀.tmp` 与 `x-￼.tmp`（公共前缀之后才分岔，首字符分岔是打不到的）。

## 3. 已登记的形状缺口（不宣称已闭合）

| 项 | 说明 |
| --- | --- |
| `rejected_rules` 只带 id | TS 的带 `{ruleId, name, problems}` ⇒ `item-rejected` 那句话点名只能是 id、复述不出"因为哪条判据被拒"。要闭合得改 `RuleReport` 的形状并给 `ProblemReason` 加 `ForbiddenRootUnresolved`。**因此 `refusals` 的对账只比 `(scope, ruleId, path, reason, bytes)`、不比 `detail`。** |
| TS 基准在一类输入上**抛异常**（不是行为不同） | 规则被整项勾选 + 该规则名下还有非字符串路径元素时，TS `preview.ts:221` 把原始元素直接塞进 `refuse`，`digestOf` 随即 `TypeError`。Rust 不崩（回 `path: null`）。**没有替 TS 改行为**；夹具刻意绕开该输入，并把缺陷登记在此。 |
| 规则表重号 | 两侧都不拦（M3-A 已登记的共同缺口）。 |
