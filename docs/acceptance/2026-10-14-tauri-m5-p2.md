## 一、四处缺陷：每一处都是「绿灯下静默失效」，不是崩溃

判据层的毛病如果报错，反而不可怕；可怕的是它把「没看成」长成「看过了」。

### 1.1 C5 的收尾码是 18，不是 259（`1891070`）

`Process32NextW` 枚举到最后一个进程返回 FALSE + `ERROR_NO_MORE_FILES`（18）。代码比的是
`ERROR_NO_MORE_ITEMS`（259），于是**每一次真机快照都被判成「中途断了」**：

```
Process32NextW 在第 264 个进程处中断（错误码 18）—— 后面的进程没进表
```

本机 `(Get-Process).Count` 当时 263 —— 枚举根本没断。后果不是错误而是**全员弃权**：C5 一旦
`Unavailable`，「无本体」那一半就取不到证据 ⇒ 238 个候选**全部** Unknown ⇒ 第 22 条提议 0 条。
238 个候选里 93 条的弃权原话**只**点名 C5（`golden-run6.log` 那一份）。

同一件事本仓 M1 已经立过判据（`crates/scanner/src/enumerate.rs` 自己定义常量 `18`；
`docs/acceptance/2026-10-10-tauri-m1.md:108` 点过「失败轮缓冲区留着旧条目」那条坑）。
P2-T2 另起一段 FFI 时又踩了一遍，原因是**这一路的用例全部喂构造好的 `ProcessSnapshot`，
一条都摸不到 FFI 那一段** —— 于是错的常量能活过整条闸。补的两条用例里关键是
`the_real_snapshot_runs_to_the_end`：不构造任何数据，当场调一次真采集，只读不起进程，
留在常规闸里。变异（改回 `== 259`）→ 2 红，还原 → 全绿。

### 1.2 一个名叫 `update` 的目录替所有 `*-updater` 作证（`b2014dc`）

本体通道走双向包含。安装根一级目录里有个 `update`，于是 `adrive-desktop-updater`
（候选名**含**条目名）被证成 **Present** —— 「这个应用还在」这句话由一个角色词说了。
审计已确认卸载的 5 条 `*-updater`（合计 **1,063.9 MiB**）全部死在这一格。

处置是 `GENERIC_ROLE_NAMES`（24 条，两侧逐条同序，TS 拿 Rust 源码对账）：条目整个就是个
角色词时，只有与候选名**整串相等**才算本体证据（留给真叫 `update` 的应用）。
**方向要写清楚**：这一条与前一轮那条「本体侧要放宽」的裁定反向 —— 它是在**收窄本体**
（少 Present ⇒ 多弃权/多提议）。换来的是「这句话到底有没有断言力」；兜底在痕迹那一半：
收窄之后多数候选落的是 Unknown 而不是 Absent。

覆盖面判据 `role_list_never_contains_a_vendor_or_os_name` 点名 `microsoft` / `windows` /
`packages` 不许进这张表：一旦进去，`%LOCALAPPDATA%\Microsoft` 再也拿不到本体证据，而它有
厂商键当痕迹 ⇒ 被判残留。这是把名单写「齐」时最可能犯的错，所以钉成用例而不是注释。

### 1.3 一个名叫 `D` 的目录替每个含 `d` 的候选作证（`b2014dc`）

把卷根补进安装根之后（§1.4），审计那 10 条**全部**翻成 Present —— 因为有个卷根一级目录
就叫 `D`。候选侧一直有 `MIN_MATCHABLE_KEY_CHARS = 3` 的长度闸，条目侧没有：**两侧同一把尺**。
顺带一处文档与代码不一致：`name_matches` 的文档早就写着「两侧都先小写归一」，代码只归一
条目侧；生产键经 `fact_key` 恒小写所以从没暴露，但调用方一旦传混大小写就**静默丢 Present**
（多删那一侧）。两侧同改，正反例各跑一次。

### 1.4 装在别的卷上、又没有卸载表条目的应用是盲区（`bbd7bdf`）

这条是**多删的方向**，比前三条都贵：第 22 条给出的 20 条 roots 里，
`%LOCALAPPDATA%\miHoYo` 与 `%APPDATA%\miHoYo` 是**假 Absent** —— 本体就在 `D:\mihoyo`
（独立口径当场命中），而注册表卸载表 85 条里没有它（游戏走自家启动器，不写 Uninstall）。
§4.4 的 `InstallLocation` 反馈环只救得了**登记了卸载项**的安装，第二条轴（卷根一级目录）
从没人看 ⇒ 少一条本体证据 ⇒ 把活应用的数据目录推上 🟠 清单，还附一句「应用确认不在这台
机器上」。处置：壳层对 A:–Z: 各一次 `is_dir`，存在的卷根 `push_standard` 当安装容器
（方向是**加 Present 证据** = 少删，与 P2-T2 裁定同向；成本每次扫描 ≤26 次 stat）。
落地：roots 20 → **17**，miHoYo 两条出局。

### 2.1 弃权的原因是同一个，而且是刻意的

8 条全部落在判据第 ③ 步：**本体四路都取证成功且全部没命中，但安装痕迹一条都没有**
（查过的痕迹只有 C2 厂商顶层键与 C6 开始菜单快捷方式两路）。卸载干净的残留恰恰就是把这两路
也擦掉了 —— 而这两路正是挡住三个反例的东西（`Claude` 是已装 MSIX、`kazumi` 在跑、
`urban-friendship-story` 里是游戏存档）。规格 §0.1「宁可整台机器一条都不提议，也不许猜」
在这 8 条上的兑现方式就是**不提**。

裁定：**不放宽痕迹**。要把这 8 条捞回来只有一条正路 —— 补真正的痕迹通道（服务 / 计划任务 /
驱动存储），那是新增覆盖面而不是给现有判据松螺丝。附带纠正一句谎：第 ③ 步原话写「无厂商键、
无快捷方式、**无服务**」，而服务从来没被查过（`TRACE_CHANNELS` 只有两路）；用户看得见的理由
串里不许点名没做的检查，两侧同改（`b2014dc`）。

### 2.2 字节没丢，但档位和默认勾选丢了 —— 这是本轮最重要的一笔欠账

那 1,592.6 MiB 里只有 **122.4 MiB**（ToDesk_Daas 80.2 + `Roaming\leigod` 42.2）以 🟠 出现，
其余按 `claimed` 表「先声明者计账」的口径落进了形状规则名下。下面每一格都是从
`m5-p-golden-report.json` 的 `allPaths` 里按路径串加出来的实测值，**不是**把 1,592.6 拆开：
这些目录内部还有一部分被判据排除（`ProtectedAttrs` / `PackageTree`）或根本没人认领
（`adrive` 内部只剩 4 个几 KB 的文件），所以各格加起来**不等于** 1,592.6 —— 本节只主张
「这些字节现在挂在哪条规则名下」，不主张「把审计那一栏对平了」：

```
installer-artifacts  1,063.9 MiB   ← 5 条 *-updater 里的安装包（adrive 93.5 / clash_win 82.8 /
                                       webcast_mate 374.1 / genieworkbuddy 462.9 / tidalab-updater 50.6）
app-cache-data         160.9 MiB   ← Starward\cache（1,242 个文件）
app-cache-data          82.9 MiB   ← leigod 两处内部（含 ProgramData\leigod_person_7002）
app-cache-data          61.3 MiB   ← Roaming\tidalab 内部（blob_storage 等 60 个文件）
app-cache-data          44.8 MiB   ← ToDesk_Daas 内部（与 🟠 那 80.2 并存）
```

后果不是数字虚高，而是**这些字节现在是 🟡 + 在「一键全选」里**，而审计要求它们 🟠 且不进
默认勾选（`recoverable: false` —— 卸载残留不会自己长回来）。~~机制是表序：第 22 条排在最后，
而 `installer-artifacts` / `app-cache-data` 在前面先把地盘认领走了。~~

**更正（本节写完当晚，按代码自己的机制复推）**：那句「机制是表序」只对**第 22 条真提议了的那两格**
成立。`engine.rs:604-605` —— 第三种采集模式只在 `Some(AppFact::Absent)` 时才去收子树，
`Present` / `Unknown` 走 `exclude()` 直接返回；**弃权候选从不 `take_file`，所以它在任何表序下都不可能是
赢家**。拿 `m5-p-golden-report.json` 的 `allPaths` 按「落在第 22 条那 17 个 roots 之内」实算：

```
app-cache-data      落在 17 根之内  60.09 MiB / 602 文件（i4Tools、Softdeluxe、ToDesk_Daas、Roaming\leigod）

────────────────────────────────────────────────────────────────

换不回 = 1,300.75 MiB / 2,417 文件（8 条弃权条目内的字节）⇒ 只能靠 §2.1 那条痕迹通道

修法只有一处、且不复杂：把第 22 条移到那六条**之前**（既有 15 条基线仍在最前，逐字节不变
那条性质不受影响），让「这台机器上这个应用已经没了」这一条事实**优先于**「这堆文件名字像缓存」。
本轮没做，因为它同时改动 6 条规则的 roots/字节在两侧测试与夹具里的期望值，属于一次独立的
口径变更，不该塞在一轮修缺陷的尾巴上。**记为 M5-P3 第一优先。**
>

> 不是本节一直引用的 1,413.8 MiB。差额 1,300.75 MiB 挂在**弃权**的 8 条条目里，而弃权候选从不

判据自己说自己「应用不在了」不算证据，所以拿另一套工具（PowerShell：卸载表三根 + `Get-AppxPackage`

```

**17 条全部四路无证据**（无卸载项、无 Appx、无快捷方式、无安装目录）。这条判据的非空对照
同时跑了：`miHoYo → D:\mihoyo`、`Claude → Packages\Claude_pzs8sxrjxfjjc + Claude.lnk + Appx`、
`Tencent → C:\Program Files (x86)\Tencent + D:\Tencent`、`Microsoft → 卸载表 6 条命中`，
`REG_ENTRIES_SCANNED=85` —— 也就是说这套查询**能**查出东西，17 条空是结论不是坏闸。

## 五、已观测到、未定位的一条

`cargo test --workspace` 那次跑红了 `the_ts_and_rust_tables_agree_on_this_fixture` 的自比半句
（case `claude-msix` 的 `claude`：`present` → `unknown`），而**同一份输入两次实算**按理不可能不同。
单独重跑该二进制 12 次 0 红；全量重跑 1 次 0 红。最可能是某条通道对刚 `create_dir_all` 出来的
夹具树拿到瞬时错误（共享占用 / 杀软扫描），而判据对「取不到证据」的反应是弃权 —— 方向安全，
但这仍然是**没定位**。处置：只把 `why` 原话加进出错消息（判据一字未弱），下次再红就能直接点名
是哪一路、什么错误码。**不写「已解决」，也不写「夹具漂移」。**

## 七、这张表证明什么、不证明什么

- **证明**：第 22 条在生产路径上真跑，且**只在证出 Absent 时**提议；提议的 17 条经一套
