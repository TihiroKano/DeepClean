## 1. M1-T6「以管理员重新扫描」

### 规格那句话里有一个"不许"

「提供"以管理员重新扫描"，**只提升扫描助手**」—— 这一条不是省事，是安全边界：
提权的对象只能是那个只读枚举的助手进程。把主界面提权 = 让一个带着删除按钮、
走 §16/§17/§18 确认链的进程拿到管理员令牌，那是拿便利换边界，方向反了。

推论，写在这里免得将来有人"顺手把结果合并进界面"：
**提权扫到的那些文件，非提权的执行器删不动。** 所以助手那一趟天生是"看清楚有多少"，
不是"能删多少"。要让提权结果变成可执行清单，得先回答"删除由谁执行"，
那是另一个决定，不在 T6 里，本刀也没顺手做。

### 落点

| 文件 | 内容 |
| --- | --- |
| `crates/scanner/src/elevate.rs` | 新模块。`should_offer_elevation(&Counters)`（纯）、`helper_command_line(root, out)`（纯）、`launch_elevated(exe, params)`（`ShellExecuteExW` + `runas`） |
| `crates/scanner/examples/scan_one.rs` | 加 `--out=<路径>`：`.tmp` 写完 `rename`（轮询方看到目标文件时必然是完整那一份），失败也落一个 `{"error":…}` 免得对方干等 |
| `crates/scanner/examples/elevate_probe.rs` | 真机跑手（会弹 UAC），四相各打一行事实 |
| `crates/scanner/Cargo.toml` | 加 `Win32_UI_Shell`；**外加 `Win32_System_Registry`** —— windows-sys 0.61 把 x86_64 那份 `SHELLEXECUTEINFOW` 门在这个跟注册表毫无关系的 feature 后面（少了它报 "no SHELLEXECUTEINFOW in Shell"，32 位那份才门在 `target_arch`） |

### 判据只认 `denied`（两格"看着像扫不全"明确不算）

`should_offer_elevation` = `counters.errors.denied > 0`。写进用例逐格点名的两格**不**触发：

- `skipped_reparse`（900 条也不触发）—— junction 一律不进入是 §28 原则二，提权也不会变，
  问了 UAC 只是白打断用户一次；
- `depth_capped` —— 撞到的是参数上限，改参数就行，跟管理员令牌无关。

### 命令行构造那两个经典坑（单测钉的正是它们）

- 带空格的路径整体加引号；
- **尾部反斜杠必须先去掉** —— `"D:\some dir\"` 里的 `\"` 是转义引号，引号被吃掉、后面的参数整段粘进来。
  用例 `a_trailing_backslash_before_a_quote_is_not_an_escaped_quote` 直接断言结果不以 `\` 结尾；
- `--out=` 恒在（`the_out_flag_is_always_there`）：提权跑的是另一个进程，
  stdout 回不到这个非提权进程 —— 没有落盘路径就等于拿不到结果；
- `launching_a_missing_helper_fails_before_touching_uac`：助手不在盘上时**先报错，不弹框**。
  用户点了"是"之后才发现起不来，是最坏的一种失败顺序。

### 真机那一跑（UAC 由人点的，这一格不能自动化 —— 也没假装能）

`cargo run --release -p deepclean-scanner --example elevate_probe -- "C:\Windows" "<scan_one.exe>"`，
exit 0，原样输出：

```
PROBE 1 非提权：files=125123 dirs=35374 denied=46 用时=14426ms
PROBE 2 判据：denied > 0 ⇒ 该提权重扫（现在会弹 UAC，请点"是"）
PROBE 3 助手参数串：C:\Windows --out=D:\dc-tmp\deepclean-elevate-probe-16160.json
PROBE 4 提权：files=128851 dirs=38592 denied=3（非提权是 files=125123 denied=46）
PROBE 结论：多扫到文件 且被拒变少 ⇒ 提权真的看见了之前看不见的东西
```

判据是**两半**，缺一半都不算过（跑手自己会 exit 7）：提权后 `files` 必须变多 **且** `denied` 必须变少。
理由写在文件头：一次什么都没多扫到的提权完全可以"成功"（UAC 点了是、助手跑了、报告照样那份），
那种成功什么也没证明。实测多出来 **3,728 个文件 / 3,218 个目录**，被拒从 46 掉到 3。

一个必须点名的口径注脚：`C:\Windows` **不是静止夹具** —— 同一台机器同一棵根，
M5-F 那趟量到 `files=125,125 / dirs=35,377`，这一趟是 `125,123 / 35,374`。
差的是 Windows 自己在两次跑之间动过的文件，不是扫描器漂了。
所以这两份数**不能**拿来互证"扫描器正确"（它们共享同一个盲区），
真正互证的是 M5-F §0 那棵静止夹具的三轴逐位对账。

### 没做的那一半（点名，不含糊）

- **界面没有"以管理员重新扫描"那颗按钮。** T6 的范围就是"判据 + 命令行构造 + 薄封装"
  （计划里明写），而接上界面还要求先回答"提权扫到的树怎么并回这个非提权会话"——
  上面那条推论说明它不是一个纯 UI 活儿。今天 `should_offer_elevation` 在生产路径上**没有调用方**，
  只有探针在调它。这一格留给"要不要做提权合并"这个决定，不做就一直是这样。
- UAC 被点"否"的那一支（`E_UAC_DECLINED` / `E_UAC_DENIED_BY_POLICY` 两条串分开写了）
  **没有真机跑过** —— 要跑它得再点一次"否"。逻辑与错误码（1223 / 5）来自文档，不是实测。

> ### 2026-10-25 订正：`asInvoker` 那条裁定被推翻
>
> 上表后两行是**当时的读数与当时的裁定**，原文划掉保留、不重写 —— 它们确实成立过。
> 推翻它们的是 2026-10-24 一次真机清理的逐条账（任务 `auto-1792854191063-1`）：
>
> | 读数 | 数量 |
> | --- | --- |
> | 失败条目 | 2167 |
> | 其中 `WIN32_120`（`DE_ACCESSDENIEDSRC`） | 2154 |
> | 仍存在的失败目标里，`BUILTIN\Administrators` 有 Delete 权 | **2164 / 2165** |
> | 被正在运行的进程锁住（提权也删不掉） | 14 |
> | 只有 TrustedInstaller 能删（提权也删不掉） | 3 |
>
> 2164/2165 有 Delete 权却删失败，说明这些字节**只**因为进程是 Medium 完整性级别而删不掉。
> 那不是「用边界换便利」，是「边界换来了一个永远删不掉的结果」。
> 人类伙伴 2026-10-25 裁定：启动即提权。
>
> **本条 §1 里那句推论也随之作废**：「提权扫到的那些文件，非提权的执行器删不动……
> 得先回答删除由谁执行」—— 现在答案是主程序自己以管理员运行。
>
> 代价如实登记（不因为改了就往小写）：
> 1. 整个带删除按钮的界面常驻管理员令牌，§16/§17/§18 那几道闸从「纵深防御的一层」
>    变成「唯一的一层」；
> 2. 双击即弹 UAC，拒绝则应用不起；
> 3. 提权**也删不掉**的两类仍在（上面那 14 + 3 条），所以界面那条提示说的是
>    「仍可能删除失败」，不是「都能删掉」。
>
> 落地与验证（2026-10-25）：
> - `src-tauri/windows-app-manifest.xml` 的 `requestedExecutionLevel` 改 `requireAdministrator`；
> - `src-tauri/build.rs` 按 profile 分档：release 嵌提权档，**debug 档替换成 `asInvoker`**
>   —— 否则 `cargo test` 起的测试 exe 也要提升，实测整包 124 条一条都跑不起来
>   （`os error 740`）。判据只能用 `PROFILE`：build script 拿不到「这次是不是 `--test`」
>   （实测 `CARGO_CFG_TEST` / `CARGO_BIN_NAME` / `CARGO_PRIMARY_PACKAGE` 全是 `None`）。
> - 实测读数：release `deepclean-app.exe` 里活着的 manifest 块**恰好 1 份**，
>   含 `requireAdministrator` ∧ `longPathAware` ∧ `Common-Controls`，不含 `asInvoker`；
>   debug 那份反过来（`asInvoker`，不含 `requireAdministrator`）。
> - 代价登记：**debug 档复现不出「提权后能删」**，要验那条必须跑 release 产物或装出来的包。
>
> 未做：安装包尚未重打（`bundle` 那一步没跑），所以
> `docs/acceptance/2026-10-15-m6-packaging-gate.md` 里那份 221,878,005 B 的 setup.exe
> **仍是不提权的旧产物**。要分发前必须重打并复验那条读数。

如果 `ld` 留下的是另一份（默认清单）而把 tauri 那份丢了，`longPathAware` 会是 0 次 ——
它是 1 次，所以活下来的正是带 `longPathAware=true` 的那一份。
对一个磁盘扫描器来说这条不是洁癖：`longPathAware` 决定不以 `\\?\` 打开路径的那条路能不能吃到长路径
（扫描器自己走 `\\?\`，所以这条是"顺带也要对"，不是唯一防线）。

**没查的部分，点名**：重复那份清单到底由哪个目标文件带进来（`tauri_build` 的 winres 产物、
还是 mingw 运行库自己那份），没去定位；`.rsrc` 目录里 RT_MANIFEST 的条目数也没解析成
（我写的 PE 头解析器把节表偏移算错了 4 个字节，修它的时间不值 —— 上面那张表已经能定结论）。
所以这句是"产物是对的"，不是"链接器为什么抱怨"。
