## 0. 先对账，再谈快慢

"扫得快"只有在"扫到的是同一棵树"时才有意义，所以第一张表是口径对账，用的是
`scripts/oracle.mjs`（PowerShell 独立口径，带 `\\?\` 前缀，且 `enumErrors=0` 才肯出数）。

| 量 | oracle 全树 | 减去登记过的 `System Volume Information` 子树 | 扫描器（release `scan_one`） |
| --- | --- | --- | --- |
| 文件 | 100,006 | 100,006 − 10,205 = **89,801** | **89,801** ✓ |
| 目录 | 62（不含根） | 62 − 5 = **57** | **57** ✓ |
| 表观字节 | 1,033,725,042 | 1,033,725,042 − 1,285,990 = **1,032,439,052** | **1,032,439,052** ✓ |

**三轴逐位相等**，不是"接近"。

这一格差点被我做错两次，都记下来：

1. 第一版我拿朴素的 `Get-ChildItem -Recurse -Force`（不加 `\\?\`）数出 **97,974**，与扫描器差 8,173，
   当时脑子里冒出的第一个解释是"扫描器少报了 8 千个文件"。真相是两边**各错一边**：
   本机 `LongPathsEnabled = 0`，朴素枚举在 >260 字符那一支**静默少计 2,032 条**（oracle 头部点名过的
   实测坑），而扫描器按 `SKIP_ALWAYS` 整块跳过 SVI 子树 10,205 条 ——
   `97,974 − (10,205 − 2,032) = 89,801`，闭合。
   **一个自己就带盲区的数，没有资格判定另一个数错了。**
2. 字节那一轴我第一版比的是 `bytes_counted`（**占用**口径），差出 295,788 字节。
   oracle 的 `Length -Sum` 是**表观**，对应的字段是 `bytes_logical` —— 换成同口径那一份就是 0 差。
   与 §⑤ 那格「目录数 +1」是同一类错：**判据的口径没读就来比**。

## 1. 耗时与驻留

| 树 | 文件 / 目录 | wall（release 扫描器） | peak RSS（扫描器进程） |
| --- | --- | --- | --- |
| `D:\deepclean-fixture\f100k` | 89,801 / 57 | **178 ms** | **16.9 MB** |
| `C:\Windows` | 125,125 / 35,377（denied 46） | **11,607 ms** | **53.4 MB** |
| 对照：M1 的 `C:\` 全盘（`docs/acceptance/2026-10-10-tauri-m1.md`） | 473,329 / 95,475 | 15.6 s | 132.5 MB |

同一条 `crates/scanner/examples/scan_one.rs`、同一个 `GetProcessMemoryInfo` 口径，
所以第三行是**可比的**而不是修辞。十万级这一档：不到 0.2 s、驻留 17 MB。

界面跑的是 **debug** 构建（`cargo test` / `target/debug/deepclean-app.exe`），同一台机器上：
f100k 521 ms、`C:\Windows` 20.9 s —— 慢 2.4–4×。
**下面所有"卡不卡"的结论都是在 debug 上量的，即按最坏那一档量的。**

## 2. 锁里那三段（这才是"卡界面"的真身）

`service::build_preview` **抱着会话锁走完整个函数**（那里的注释点名了这件事），
里面依次做：`rule_report`（引擎整树评估）→ §12 归属反查 → `dup.findings_for`。
扫描线程发布进度要拿的正是同一把锁。所以"卡不卡"不是一句感觉，而是这几段各花多少毫秒。

| 段 | f100k（58 目录 / 89,801 文件） | `C:\Windows`（35,332 目录 / 125,125 文件） | 形状 |
| --- | --- | --- | --- |
| `rule_report` 整树评估 | 8.8 ms | 156.8 ms | O(目录数) |
| `knows_path_in_tree` 命中 | 163 µs | 3.9 ms | O(目录数 + 该目录内文件数) |
| `knows_path_in_tree` 落空（最坏） | 103 µs | **70.6 ms** | O(目录数)，每条分配一个 `normalize_key` 串 |
| `findings_for` 勾 1 组（缓存里 20,000 组） | 6.3 ms | 4.9 ms | **O(总组数)**，与勾了几组无关 |
| `findings_for` 勾全部 20,000 组 | 689 ms | 694 ms | 同上 + 输出构造 |

两条轴分开量是**必须的**：`f100k` 是"文件多、目录少"（89,801 文件 / 57 目录），
拿它量逐目录线性扫的 `knows_path_in_tree` 会得到一个好看的假数（103 µs）。
换成目录多的 `C:\Windows` 才是那一判据的真身 —— 70.6 ms。
仪器：`src-tauri/src/perf.rs`（`#[ignore]`，`DC_PERF_ROOT` 指定量哪棵树）。

### 裁定（两条，写下代价，不回头问）

- **`knows_path_in_tree` 70 ms/次：今天不建索引。** 它是"一次点击一次"（只有
  `dc_reveal_path` / `dc_open_item` 两个消费点，都是点击驱动），不是每帧、不是逐行；
  换来的是给 35k 目录建一张路径哈希表 + 一份必须跟着树失效的缓存。
  **代价**：这条判据现在是"点击级"的，谁把它放进逐行渲染（比如给表里每一行问一次"认不认"），
  它就变成 O(行 × 目录) —— 那时必须先建索引。这一句写在这里就是为了下次不用重新发现。
- **`findings_for` 是 O(总组数)，全勾 20,000 组要 0.7 s（且发生在锁里）。**
  这一格的规模是**合成的**：`make-fixture.mjs` 写的是随机字节，f100k 里**没有**重复内容，
  真盘上到底会有多少组今天没有数。所以这里只能说"形状与单位成本"，
  不许写成"真盘实测 0.7 s"。**代价**：真盘组数那一格仍然空着，要它得先在一次真 `C:\` 重复检测里
  记 `groups.length`（那是 M5-B 那条链上的事，不在本刀）。

## 3. 真机：扫描途中界面动不动（`scripts/m5f-perf-e2e.ps1`，exit 0，六图）

目标选 `C:\Windows` 而不是 f100k：后者 release 下 178 ms 就扫完，**根本来不及观察**。
脚本六相，跑的是 debug 构建（最坏那一档）。最后一跑（exit 0）：

| 相 | 判据（认的是屏幕上的形状，不是日志） | 这一跑 |
| --- | --- | --- |
| ① | 首页「已扫描文件」连采 5 个点，**每一轮都拿到新数字** = 渲染进程在更新、`dc_snapshot` 往返在完成 | `196 → 3,675 → 6,129 → 6,791 → 11,245` |
| ② | 就在此刻点「大文件」→ 1 s 内换页。认的是那页独有的表头「Top 100」—— 侧栏文字常驻，拿「找得到首页两个字」判换页是恒真断言 | 604 ms，落在进度 9% |
| ③ | 途中把另外三页各开一次（「重复文件」/「垃圾清理」/「开发环境」），逐页截图并把它说的话打进日志 | 三页都开到了；抓出 §4 的第二处缺陷 |
| ④ | **停在「大文件」什么都不点**，等它自己从「这一轮还在扫」念出数 | 39.6 s 后出现「100 项 · 合计 5.1 GB」 |
| ⑤ | 回首页继续采样到扫完，全程采样点严格递增 | 终值 125,125，与扫描器自己的 `files=125,125` 逐位一致 |
| ⑥ | 进程树（主进程 + WebView2 那几个）的工作集与峰值点名 | 8 个进程，峰值 621.4 MB |

四件事必须点名：

- **③ 那一相是 §5 里自己欠下的账，这一趟兑现的**：§4 那几个缺陷全是"第一次在扫描途中打开
  那一页"撞出来的，所以不能假定另外三页没问题。结果两页干净、一页说假话（见 §4）。
- **④ 是单测看不见的那一格。** `renderToStaticMarkup` 不跑 effect，把 `running` 从
  `useCallback` 的依赖里拿掉，六条用例全绿（变异 L4 实测：一条都不红）。
  所以"扫完会不会自动重问"只能在真窗口上量 —— 那一相就是为它加的。
- **⑥ 的数按跑次漂**：同一台机器、同一条脚本，六跑分别是 517.8 / 522.8 / 528.0 / 655.9 /
  615.7 / 621.4 MB。所以这里只登记区间、不拿单次当结论，也**不设阈值**
  （没有同口径的可比基线；硬编一个"应当 < 300 MB"就是自己出题再自己答对）。
  对照 §1 那行"扫描器自己那份数据 53.4 MB"，差值是 web 栈的常驻，Electron 线同样要付这一笔。
- 终图 `m5f-after-scan.png` 拍到的是**空间地图**而不是首页：扫完后应用按规格自动跳图
  （`App.tsx:86-91`，只在用户还停在首页时跳）。于是那张图顺带成了"125k 文件 / 35k 目录
  的 treemap 画得出来"的证据，右下那句「部分数据无法访问 · 共跳过 46 个」
  与扫描器 `denied=46` 逐位一致。

## 4. 这一趟顺带抓到的四个界面缺陷（都修了，全都只有截图看得见）

判据来自测量本身：为了量"途中点导航"，才第一次在扫描途中打开那一页。

| 缺陷 | 屏幕上是什么 | 为什么算缺陷 | 修在哪一层 |
| --- | --- | --- | --- |
| 措辞 | 扫描途中的「大文件」写着「0 项 · 合计 0 B」+「无匹配大文件。」 | 真相是"树还没 publish、这一轮还在扫"（`st.tree` 为 `None` ⇒ `dc_top_files` 回空表，那是 M5-E④ 定的口径）。「无匹配」是一个**看起来正常的假结论**，本项目把这一类点名为缺陷 | 那一页拿到 `status`，`running` 那一支换成一句真话；扫完自动重问（依赖里加 `running`） |
| 同一族的第二处 | 扫描途中的「垃圾清理」：上面一行明明白白写着「本次扫描状态是「running」，下面的数字只是已扫到的部分」，**同一屏**下面一行是「扫描会话已失效（请重新扫描）」 | 服务端 `build_preview` 的 `null` 是**两件事塌成的一个值**：会话真没了，和"还在扫、树上没有完整数据"。两句话在同一屏互相打脸 | 抽一个纯函数 `previewNullMessage(status)` 分说两句；`usePreview` 那个参数本来就在收 `status`（只是类型写成了 `unknown`） |
| 顶栏被挤 | 第一版把整句解释放进顶栏 → 「Top 100 大文件」与「刷新」各被拆成两行 | 读 `textContent` 的判据抓不到几何错位 | 顶栏只留短句（长度 ≤12 由用例钉住），完整解释挪进下面的空态（整行排版不挤谁） |
| 操作列 | 「打开位置」被拆成一列竖排的单字；加了 `nowrap` 之后又整列被推出右边界，只剩横向滚动条找得到它 | 自动布局下 `max-width` 在 `<td>` 上**不被遵守** —— `C:\Windows\...\FileRepository\nvnhqi.inf_amd64_…` 这种长串把位置列撑到无限宽 | `.dc-large .dc-table { table-layout: fixed }` + 六列点名宽度（与 §3.6 开发环境页同一味药），操作列用 `.dc-td-act` 拿自己的下限 |

**另外两页是干净的**（这一趟也各开了一次，不是推断）：「重复文件」途中挂着
「扫描没跑完不许开查：半截的树上「没找到另一份」多半只是还没扫到」，
「开发环境」途中是「正在问这台机器装了哪些工具链…」 —— 两句都是真话。
扫查的判据用"页面标题那一次**额外**出现"（侧栏项与页面标题同名，拿文字在不在判换页是恒真断言；
第一版想用 UIA 的 `ControlType=Header` 精确定位，实测 Chromium 不把这些 `h2` 报成 Header，
查询恒空，于是"换页成功"永远判不出来）。

钉住的方式分两层，缺一层都不算数：

- 单测 `tests/unit/largefiles-live.test.tsx`（6 条）与 `tests/unit/preview-null-message.test.tsx`（3 条）
  钉前三个。**两条轴都钉**：`running` 时不许出现「无匹配大文件」/「失效」；
  `completed` 且真的空时「无匹配大文件」/「失效」必须在 —— 只钉一支的话，把分支条件反过来照样绿，
  而真事故恰恰是反方向的（扫完了、真的没有大文件、会话真的没了，界面却还挂着"还在扫"）。
  变异电池：L1 拿掉那一支 → 红 2；L2 条件反过来 → 红 3；L3 只改文案不改判据 → 红 2；
  **L4 把 `running` 从依赖里拿掉 → 一条都不红**（于是有了 §3 的 ④ 相）；
  P1 状态集合写错 → 红 2；P2 两句话对调 → 红 2；P3 塌回一句 → 红 2；P4 漏掉 `paused` → 红 1。
  其中 **P3 之前先红了一次自己的用例**：第一版新句写的是「…（不是会话失效）」，
  含「失效」二字，被"还在扫那一支不许出现失效"当场挡下 —— 判据先抓到了作者。
- 第三个和 §3 的 ④ 相只能靠眼睛：`m5f-largefiles-filled.png` 三版对看
  （拆成一列竖排的版本 / 整列被推出边界的版本 / 现在这版）。
## 5. 没验什么（点名）

- **真盘重复组数**没有数（§2 那条裁定点名了）。
- **500k / 1M 档**（`f500k`、`fat-1000000` 两棵静止夹具在盘上）没跑 —— 规格那一格写的是十万级，
  更大档要的是"内存会不会先爆"，而那要另一套采样与闸门，不在本刀。
- **峰值工作集没有阈值**（§3 的 ⑤ 相说明了为什么宁可不设，也记了跑次之间的漂移）。
- 界面那半边是 **debug 构建**；release 界面只会更快，所以"不卡"这个结论是保守方向的，
  但**耗时数字不可跨档引用**。
- **途中扫查只覆盖到"打开那一页看它说什么"。** 三页各开一次的判据是页面标题那一次额外出现，
  它证明的是"页挂了、话说得对不对"，不是"那一页在途中被**操作**会怎样"
  （比如途中点「开始查找重复文件」—— 那一格自己带了"扫描没跑完不许开查"的禁用，
  但没有逐个点过）。
  > **2026-10-13 追记（M5-J）**：这一条还了一半 —— 检测**跑起来之后**途中的导航与「取消」
  > 都在真机上点过了（`docs/acceptance/2026-10-13-tauri-m5-j.md` §1）。
  > 仍然没点的：途中改门槛值重跑、途中勾选某组进预览。
- **横向滚动条本身没被消灭**，只是不再需要它才能点到操作（定布局之后六列各自有份）。
  窗口再窄一档会怎样（比如 900 px 以下），没量过。
