# Tauri 重写 · M5-L 验收：`rejectedRules` 的线形状与 TS 对齐（2026-10-13）

任务出处：`docs/superpowers/plans/` 的 M5 批次清单 + 上一轮盘点里那条
「Rust 侧 `rejected_rules` 只有 id，TS 侧是 `{ruleId, name, problems[]}`」。
本条**不改删除语义**，也不新增删除能力；改的是声明层拒规则时**留下的那一份说明**够不够下游念出来。

---

## 1. 这条缺口为什么不是纯洁癖

`core/rules/types.ts:216` 的 `RejectedRule` 带三格：`ruleId` / `name` / `problems[]`。
Rust 侧原来是 `Vec<String>` —— 只有 id。

下游正是 §17 预览那句 `item-rejected` 拒绝理由（`core/rules/preview.ts:121-127`）：

```
规则「相对路径」在 §15 声明层就被 validateRuleSet 拒了（invalid-shape），报告里没有它 → 不计入预估
```

只带 id 时，Rust 侧念出来的是（改前逐字）：

```
规则「windows-temp」在 §15 声明层就被 validate_rule_set 拒了，报告里没有它 → 不计入预估
```

用户读到的是一个**内部标识**而不是规则名，而且**完全没有原因** —— 原因藏在排除清单里，
而预览那句不查排除清单。这不是"文案不好看"：那句的存在意义就是回答"我勾了为什么不算钱"，
少了原因就答不了。

## 2. 改了什么

| 文件 | 改动 |
| --- | --- |
| `crates/rules/src/engine.rs` | 新增 `RejectedProblem` / `RejectedRule`；`RuleReport.rejected_rules` 从 `Vec<String>` 换成 `Vec<RejectedRule>`；两条构造路径（fail-safe 与校验层）都按 TS 同形填 `name` + `problems` |
| `crates/rules/src/engine.rs` | `rule-rejected` 那条**排除记录**与**进表**合进同一个带筛子的循环（原来在两个循环里，筛子只有一边有） |
| `crates/cleaner/src/preview.rs` | 消费方按 `rule_id` 找到那条被拒规则，念 `name` 与逐条 `reason`（`、` 连接），`problems` 为空时退到「未记录具体原因」 |
| `scripts/parity-rules.mjs` + `crates/rules/tests/parity_with_ts.rs` | 对账投影从「只比 id 的集合」换成 `{ruleId, name, problems:[{reason}]}`，外层按 ruleId 升序、**内层不排序**（问题次序是判据的一部分） |
| `crates/cleaner/tests/data/preview-parity.json` | 新增 ruleSet `declared-rejected` 与同名 case（见 §5） |

`RejectedProblem.reason` 存的是**线上串**（kebab-case 字面量）而不是再立一个枚举：
TS 那边 `RuleProblem = Exclusion`（同一个类型），Rust 侧校验层的 `ProblemReason` 与排除记录的
`ExclusionReason` 是两个类型（`invalid-shape` 根本不在后者里）。硬并成一个枚举会改到排除面的类型，
而消费方要的本就是那个串。

## 3. 跨实现对账（这条的主要证据）

`crates/rules/tests/parity_with_ts.rs` 现起 esbuild + node 跑 TS 引擎，两侧同一份夹具
`crates/rules/tests/data/m3-parity.json`，零容差。投影加宽后，四个 case 里 `rejectedRules` 的真实内容：

| case | 条数 | 内容 |
| --- | --- | --- |
| `builtin` | 0 | 内置表没有声明层问题 |
| `gates` | 0 | |
| `blocked` | 2 | `n`(npm) / `t`(临时)，各挂一份 `forbidden-root-unresolved` |
| `static` | 6 | `ancestor-of-protected` ×2、`broad-container`、`report-only-root`、`invalid-shape`、`pattern-not-leaf` |

原来这一格只比 id 集合，所以 `name` 与逐条 `reason` **从来没被人比过** —— 而它们正是那句文案的原料。
加宽后两侧逐字相同（`detail` 仍不比：散文，两侧各写一遍，与排除项同一条 posture）。

### 已登记的字段位置分歧：`problems[].path` 不进比较

`static` 那条 `relative` 规则（paths 写了相对路径）两侧信息都不缺，只是落在不同格子：

- TS `engine.ts:226` 调 `problem(r.id, 'invalid-shape', …)` ⇒ `path` = **规则 id**，出问题的模板在 `detail` 串里；
- Rust `validate.rs:121` 给的是**那个模板** ⇒ `path` = `AppData\Local\Temp`。

处置是**显式不比这一格**并把原因写在投影函数旁边，而不是单方面改一侧的字段语义（`path` 是要上界面
排除面板那一列的字段），也不是把它算成一致替它背书。这与 `exclusion_key` 里「`rule-rejected` 不比路径」
是同一条判据的两次落地；那里的旧注释（声称 Rust 写 `""`）已与代码矛盾，本轮改成现在真正的原因。

## 4. 两条筛子：让「进表」与「排除记录」走同一个结构

TS 的循环（`engine.ts:714-720`）先筛再记：问题指不到具体规则、或那条规则其实通过了校验，
都**不算整条被拒**，`rule-rejected` 那条排除也不写。Rust 原来把排除写在**另一个没有筛子的循环**里。

今天两侧行为仍然一致 —— 因为 `validate_rule_set` 每个 `push` 之后紧跟 `continue` 或
`rejected = true; break`，一条规则最多产一份问题，`valid` 与 problem 互斥，两条筛子都不落地。
但那是一致写成巧合。本轮把两个循环合成一个，一致写成结构。

## 5. 预览那条分支原本没人比过（本轮补上）

跑一遍 `scripts/parity-preview.mjs` 数原语：六个 case 里 `item-rejected` **命中 0 次**。
按 id 猜原因：内置 `main` 那套规则全部有效（要么产 finding 要么被环境筛掉），
所以被声明层拒掉的规则从来没进过预览的选择清单。那句话是**防御分支**——
真机上点不出来（界面上能勾的项来自 findings，而被拒的规则不产 findings），
只有外部拼装的选择（第三方调 §17、或将来规则表里真混进坏规则）才走到。

所以验收不能靠截图，得靠夹具。新增 ruleSet `declared-rejected`（一条有效 + `invalid-shape` ×2 +
`report-only-root` ×1）与同名 case，跑出来的结构（`scope=item` / `ruleId` / `path=null` /
`reason=item-rejected` / `bytes=0`）两侧逐格相同，`detail` 被投影摘掉（措辞不比）。
这条 case 加进去第一次就红了一次，红得有价值：我写的 `category: "system"` 不在
`RuleCategory` 的八个变体里，Rust 侧 serde 大声拒绝（TS 侧不校验、会静默接受）——
这正是两侧的一条真实形状差，只是本轮不需要它。

## 8. 没做与代价

1. **`path` 那一格仍是两套放法**（§3 末）。要统一必须单方面改一侧的字段语义，而它上界面。
   代价：排除面板之外没人受影响，但跨实现对账在这一格永久失明。
2. **`detail` 不进任何比较**（两侧各写一遍散文）。预览那句的中文措辞靠各自单测钉住：
   Rust 侧断言句里含「坏规则」与「invalid-shape」且**不含**内部 id「bad」，另有一条空 `problems`
   的用例钉住「未记录具体原因」那一路。
3. **函数名那一格两侧不同**（TS 念 `validateRuleSet`、Rust 念 `validate_rule_set`）：各侧写真跑的那个，
   与"散文各写一遍"同 posture；已在消费方注释里写明，避免下一轮误读成"逐字相同"。
4. **这一句真机上点不出来**（§5）。它只在外部拼装选择时出现，所以本轮的验收是夹具而不是截图；
   没有为它加 dev-only 入口（那会让一个防御分支看起来像被测过）。
5. **不改删除语义、零新删除代码**，也没有新增任何执行入口。
